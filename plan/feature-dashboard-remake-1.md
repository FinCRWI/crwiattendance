# Introduction

![Status: Planned](https://img.shields.io/badge/status-Planned-blue)

Remake the dashboard layout to enforce a consistent reading order for staff (Feast → Team Activity → remaining widgets), centralize dashboard customization under admin control via a new widget (with a dedicated `customize: admin` permission), and add a toggle that optionally applies the same customization to the Global Admin dashboard. The spec defines three user personas:

| Persona | Identifier | Condition |
|---------|-----------|-----------|
| Global Admin | `globalAdmin` | `user.isAdmin === true` |
| Admin with customize rule | `customizationAdmin` | `hasPerm('customize', 'admin', user) === true` |
| Partial admin (other admin perms) | `partialAdmin` | `canSeeAdminPanel(user) === true` but NOT `hasPerm('customize', 'admin', user)` |
| Regular staff | `staff` | None of the above |

## 1. Requirements & Constraints

- **REQ-001**: Team Activity widget must appear directly below the Feast section for all non-admin users (`staff` and `partialAdmin` personas). Admin users (`globalAdmin` and `customizationAdmin`) keep Team Activity in its current position.
- **REQ-002**: Dashboard customization must be removed from per-user scope and centralized under admin control. Only users with `customize: admin` permission can access the customization widget.
- **REQ-003**: Customization changes made via the admin widget apply globally to all staff dashboards. No per-user overrides are permitted.
- **REQ-004**: A toggle inside the admin customization widget must control whether the Global Admin dashboard mirrors staff customization (default: off — Global Admin dashboard stays independent).
- **REQ-005**: The customization settings document must be stored in Firestore at `settings/dashboard_customization` for persistence across sessions.
- **REQ-006**: Customization settings must be fetched on dashboard render and applied before the DOM is constructed (no flicker or layout shift).
- **SEC-001**: The Firestore security rules for `settings/dashboard_customization` must restrict writes to users with `customize: admin` permission. Reads must be allowed for all authenticated users.
- **SEC-002**: The `customize` permission module must be created in `permissions.js` following the existing pattern (line 31–41 of `js/modules/permissions.js`).
- **SEC-003**: No customization setting may expose or modify sensitive data (user PII, attendance records, etc.).
- **CON-001**: The `detailSectionHTML` variable is built inline within `renderDashboard()` at `js/ui/dashboard.js:2200-2258`. No `renderDetailSection` function exists — refactoring into one is out of scope for this plan.
- **CON-002**: The `primaryRowThirdCard` variable (line 2202, rendered at lines 2236/2250) is the Team Activity widget card generated by `renderActivityLog()` at `js/ui/dashboard.js:1167`.
- **CON-003**: All new CSS must be scoped under `.dashboard-staff-view` to avoid affecting admin layouts, following the pattern established at `css/dashboard-modern.css:2265`.
- **CON-004**: Customization widget UI must follow the existing card pattern used by other dashboard widgets (card with heading, border-left accent, internal grid/flex layout).
- **GUD-001**: Follow the existing ES module pattern — singletons exported from `js/modules/` and `js/ui/` files, `window.*` aliases for cross-module communication.
- **GUD-002**: Store all hardcoded values (document paths, toggle defaults, permission module names) in `js/config.js` under the existing `AppConfig` namespace, as done for `AppConfig.DASHBOARD` at `js/config.js:110-119`.
- **PAT-001**: Permission registration pattern — export a function from `permissions.js`, then add a `window.app_can*` alias at `js/modules/permissions.js:77-86`.
- **PAT-002**: Firestore document read/write pattern — use `db.doc('collection/docId').get()` / `.set()` via the existing `AppDB` adapter, consistent with `js/modules/policies.js:30` and other settings patterns.
- **PAT-003**: Toggle UI pattern — form checkbox styled as a toggle switch, consistent with the existing toggle controls used elsewhere in the admin panel (see `js/ui/admin.js` for reference).

## 3. Alternatives

- **ALT-001**: Store customization settings per-user in a subcollection (`users/{uid}/settings`). Rejected because REQ-003 explicitly requires global application with no per-user overrides. A single settings document ensures uniformity and auditability.
- **ALT-002**: Build customization as a drag-and-drop widget reorder interface. Rejected as over-engineered for v1. The initial implementation uses simple visibility toggles and a layout density selector, which covers the core request without the complexity of sortable state management.
- **ALT-003**: Implement customization purely client-side via `localStorage`. Rejected because REQ-005 requires Firestore persistence, and admin control would be lost if staff could clear their localStorage.
- **ALT-004**: Refactor `detailSectionHTML` into a dedicated `renderDetailSection()` function. Rejected per CON-001 — out of scope for this plan. The inline template variable approach is consistent with the existing codebase pattern at `js/ui/dashboard.js:2200-2258`.

## 7. Risks & Assumptions

- **RISK-001**: The Firestore read for customization settings (TASK-019) adds latency to dashboard render. Mitigation: the `loadSettings()` call runs early in `renderDashboard()` alongside other async data fetches. Settings are small (< 2 KB), so network overhead is negligible.
- **RISK-002**: The `renderDashboard()` function at `js/ui/dashboard.js:1816` is already large (~620 lines). Adding more inline logic increases complexity. Mitigation: keep the visibility guard logic as simple ternary operators in the template; avoid nested conditionals.
- **RISK-003**: The `saveSettings` Firestore write must be debounced to avoid excessive writes when toggling multiple checkboxes rapidly. Mitigation: the event handler in TASK-015 collects changes and saves on each change; if latency becomes an issue, a 300 ms debounce can be added as a follow-up.
- **ASSUMPTION-001**: The `settings` collection and `dashboard_customization` document do not need to be pre-created. The first `saveSettings` call with `{ merge: true }` will create it.
- **ASSUMPTION-002**: All dashboard customization settings are stored in a single Firestore document (max 1 MB), which is more than sufficient for the small amount of data involved (< 5 KB).
- **ASSUMPTION-003**: The existing compact CSS classes (`.dashboard-density-compact` activation via JS at TASK-021) produce visually acceptable results for the "Compact" density option. If further refinement is needed, it can be addressed in a follow-up plan.
